## 3. Feature Flag 설계

```python
# backend/config/feature_flags.py

F1_USE_DATA_GO_KR_API = env_bool("F1_USE_DATA_GO_KR_API", default=False)
# True → 신규 Step B/C 실행, False → 기존 Supabase DB 로직

F1_REQUIRE_HITL0_APPROVAL = env_bool("F1_REQUIRE_HITL0_APPROVAL", default=False)
# True → F0 approved 필수, False → completed만으로 진행 (과도기)

F1_ENABLE_CIRCUIT_BREAKER = env_bool("F1_ENABLE_CIRCUIT_BREAKER", default=True)
F1_RAG_VERDICT_DISABLED = env_bool("F1_RAG_VERDICT_DISABLED", default=True)
# True → Step D 표시 전용, False → 기존 판정 주도 로직 유지

F1_CANARY_PERCENTAGE = env_int("F1_CANARY_PERCENTAGE", default=0)
# 0~100. 신규 로직 적용 트래픽 비율 (랜덤 샘플링)
```

**Canary 로직:**
```python
import hashlib
def should_use_new_pipeline(case_id: str) -> bool:
    h = int(hashlib.md5(case_id.encode()).hexdigest(), 16) % 100
    return h < F1_CANARY_PERCENTAGE
```

## 5. 코드 배포 순서

### P1 (기반 인프라 배포)
1. Supabase 마이그레이션 적용 → 신규 테이블 생성
2. `services/data_go_kr/` 패키지 배포 (호출자 없음, dead code 상태)
3. 단위 테스트 통과 확인

### P2 (Step 구현 병합, feature flag off)
4. `services/f1_step_a/b/c/d.py` 병합 (플래그 off로 미실행)
5. 기존 `services/feature1.py` orchestration에 분기 추가:
   ```python
   if F1_USE_DATA_GO_KR_API and should_use_new_pipeline(case_id):
       return await run_f1_new(...)
   else:
       return run_f1_legacy(...)
   ```

### P3 (HITL UI 배포)
6. 백엔드 HITL-0/1/2 엔드포인트 추가 (플래그 off로 미적용)
7. 프론트 신규 컴포넌트 배포 (기존 컴포넌트 유지)

### P5 (Shadow 운영)
8. `F1_USE_DATA_GO_KR_API=True` + Canary 0%
9. 모든 케이스에 대해 신규·기존 **두 경로 병렬 실행** → 결과 비교만 로깅
10. 불일치 분석 리포트 작성

### P6 (Canary 점진 증가)
11. `F1_CANARY_PERCENTAGE=10` → 1일 관찰 → 50 → 1일 → 100
12. 각 단계에서 메트릭 확인 (오탐률, 지연, 담당자 피드백)

### P7 (레거시 제거)
13. 기존 `f1_rag_judge`, `f1_allowed_ingredients` 읽기 코드 제거
14. 폐기 테이블 DROP

## 6. 롤백 전략

### 6-1. P6 이전 (Shadow/Canary)

**트리거:**
- 오탐률 > 10%
- 평균 지연 > 10s
- 담당자 중대 컴플레인

**롤백 절차:**
1. `F1_CANARY_PERCENTAGE=0` 즉시 설정
2. 기존 로직으로 100% 복귀 (코드 재배포 불필요)
3. 문제 분석 후 재시도

### 6-2. P7 이후 (레거시 제거 후)

폐기 테이블 DROP 이후 롤백은 불가.
- P7 착수 전 2주 관찰 기간 동안 오류 0건 확인 필수
- DROP 전 최종 승인 게이트
