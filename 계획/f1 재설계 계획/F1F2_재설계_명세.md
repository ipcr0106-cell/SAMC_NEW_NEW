# F1+F2 재설계 명세

> 작성일: 2026-04-19
> 기반 문서: [F1_재설계_인터뷰_보고서.md](./F1_재설계_인터뷰_보고서.md), [F1_공공데이터_API_탐색보고서.md](./F1_공공데이터_API_탐색보고서.md)
> 범위: F0 → F2 → F1 → F3 데이터 흐름 정리 + 비효율 해소 + 구조적 리스크 정리

---

## 1. 설계 배경

### 1-1. 재설계 목표

1. **비효율 해소**: F2가 수행한 식품유형 분류를 F1이 중복 호출하는 문제 제거 (LLM 호출 2회 → 1회)
2. **데이터 완전성**: F0 → F2/F1 변환 시 누락되던 필드(`part`, `sub_ingredients`, `alcohol_percentage`) 복원
3. **F3 공급 완전성**: F3가 필요로 하는 `category`(식약처 7대 구분) 자동 역추론
4. **GMO 플래그 전달 경로 확립**: 원재료명 키워드 힌트에만 의존하던 GMO 감지를 공공데이터 API 기반으로 정확도 향상 (F1 재구현 시)
5. **리스크 가시화**: 구조적으로 자동 해결이 어려운 문서 오입력 케이스를 HITL 설계에 명시 반영

### 1-2. 설계 철학 (인터뷰 보고서 §2 승계)

- **HITL 절대 준수**: AI는 정보 제공·집계만, 최종 판정은 담당자
- **데이터 신뢰성 우선**: 수작업 DB → 공공데이터 공식 API 전환
- **F2 분리 원칙 유지**: 식품유형 분류는 F2 로직이 담당 (단, 현재 shim 구조에서는 F1 내부 `classify_food_type()`이 동일 로직 실행)

## 2. 데이터 흐름 전체도

```
           ┌──────────────────────────────┐
           │ 담당자 (File Upload)         │
           │ · 원재료배합비율표            │
           │ · 제조공정도                  │
           │ · MSDS                        │
           │ · 수출국 라벨                 │
           └──────────┬───────────────────┘
                      ▼
           ┌──────────────────────────────┐
           │ F0 (OCR + LLM 파싱)          │
           │ OCR: OpenAI gpt-5.4-mini     │
           │       Vision                  │
           │ LLM: OpenAI gpt-5.4-mini     │
           │ 결과: pipeline_steps('0')    │
           └──────────┬───────────────────┘
                      │
         ┌────────────┴───────────┐
         ▼                        ▼
  ┌──────────────┐         ┌──────────────┐
  │ F2 (식품유형) │         │              │
  │ F0 직접 읽음  │         │              │
  │ classify_... │         │              │
  │ pipeline('2')│         │              │
  └──────┬───────┘         │              │
         │                 │              │
         └─────────────────▶   F1         │
                            │ (수입판정)    │
                            │ · F0 읽음     │
                            │ · F2 pipeline│
                            │   결과 재사용 │
                            │ pipeline('1')│
                            └──────┬───────┘
                                   ▼
                            ┌──────────────┐
                            │ F3 (서류 매칭)│
                            │ · F0 basic_info│
                            │ · F1 result   │
                            │ pipeline('3') │
                            └──────────────┘
```

**핵심 원칙:**
- F2 → F3 직접 전달 경로는 **레거시 fallback 데드코드**. F1이 항상 `food_type_hierarchy`를 채우므로 실제로 발동 안 함
- F0 → F3 일부 필드(basic_info)는 F1을 거치지 않고 **F3가 직접** pipeline_steps에서 읽음

## 3. 단계별 데이터 명세

### 3-1. F0 → F2 / F1 전달 필드

| 필드 | 원천 (F0 파싱) | 변환 함수 | 상태 |
|------|---------------|-----------|------|
| `name` | `ingredients[].name` | `_convert_f0_to_f1_ingredients` | ✅ 기존 |
| `percentage` | `ingredients[].ratio` (str→float) | `_convert_f0_to_f1_ingredients` | ✅ 기존 |
| `ins` | `ingredients[].ins_number` | `_convert_f0_to_f1_ingredients` | ✅ 기존 |
| `cas` | `ingredients[].cas_number` | `_convert_f0_to_f1_ingredients` | ✅ 기존 |
| `part` | `ingredients[].part` | `_convert_f0_to_f1_ingredients` | 🆕 **신규 추가** |
| `sub_ingredients` | `ingredients[].sub_ingredients` | `_convert_f0_to_f1_ingredients` | 🆕 **신규 추가** |
| `is_heated` | `process_info.process_codes` | `_convert_f0_to_process_conditions` | ✅ 기존 |
| `is_distilled` | `process_info.process_codes` | `_convert_f0_to_process_conditions` | ✅ 기존 |
| `is_fermented` | `process_info.process_codes` | `_convert_f0_to_process_conditions` | ✅ 기존 |
| `alcohol_percentage` | `basic_info.alcohol_percentage` | `_convert_f0_to_process_conditions` | 🆕 **신규 추가** |
| `product_name` | `cases.product_name` (F0 아님) | `_fetch_case_product_name` | ✅ 기존 |

**변경 영향:** F2 `classify_food_type_detailed()`의 `is_alcohol` 판정 정확도 향상 (`alcohol_percentage` 실제 반영).

### 3-2. F2 → F1 전달 방식

**기존 문제:**
- F1 `/run`이 `body.food_type` 또는 `body.hierarchy_override`를 받지 못하면 `classify_food_type()`을 **다시 호출** → LLM 중복 사용

**해소 방안:**
- F1 `/run` 진입 시 `_fetch_f2_result(case_id)` 헬퍼로 `pipeline_steps(step_key='2', status='completed')` 직접 조회
- 결과가 있으면 `FoodTypeHierarchy`로 변환하여 `hierarchy_override`로 주입
- `auto_classify=False`로 설정하여 LLM 재호출 방지

**우선순위 (feature1.py `Feature1RunRequest`):**
1. `body.hierarchy_override` (담당자 명시 override — 최우선)
2. **F2 pipeline_steps 완료 결과** (자동 읽기 — 신규)
3. `body.food_type` (소분류만 명시, 하위호환)
4. Step 0-FT 자동 분류 (`auto_classify=True` 기본)

### 3-3. F1 → F3 전달 필드

F3 `_build_product_info_from_pipeline`이 사용하는 `ProductInfo` 필드 공급 현황:

| ProductInfo 필드 | 원천 | 공급 방식 |
|----------------|------|-----------|
| `food_type` (필수) | F1 `food_type_hierarchy.food_type` | pipeline_steps('1') |
| `food_large_category` | F1 `food_type_hierarchy.category_name` | pipeline_steps('1') |
| `food_mid_category` | F1 `food_type_hierarchy.subcategory_name` | pipeline_steps('1') |
| `origin_country` (필수) | F0 `basic_info.export_country` | pipeline_steps('0') |
| `is_oem` | F0 `basic_info.is_oem` | pipeline_steps('0') |
| `is_first_import` | F0 `basic_info.is_first_import` | pipeline_steps('0') |
| `has_organic_cert` | F0 `basic_info.is_organic` | pipeline_steps('0') |
| `product_keywords` | F1 `ingredients[].name` | pipeline_steps('1') |
| `category` (7대 구분) | **`_infer_category()` 역추론 신규** | 아래 참조 |

**`category` 역추론 로직 (신규):**
```
1. food_large_category가 FoodCategory Literal 값과 정확히 일치 → 그대로 사용
2. is_livestock_food_type(food_type) → "축산물"
3. 판단 불가 → None
```

**해소된 버그:** 이전에는 `category=None`이어서 `협약체결국수산물` 조건이 조용히 실패(fallback 부재) → 수산물 수입 시 필요 서류 누락. 이제 `food_large_category="수산물"`이면 `category="수산물"` 자동 주입됨.

## 5. 새 파이프라인 (인터뷰 보고서 §8 승계·확정)

```
[전제조건]
  ├─ F0 status = completed ✓
  └─ F2 status = completed ✓ (F1이 F2 결과 재사용 목적)

[HITL-0] F0 파싱 결과 검토 (신규 제안 — §7 리스크 섹션 참조)
  └─ 담당자가 파싱된 원재료·공정·기본정보 검증·수정

[Step A] 금지원료 체크 (최우선)
  ├─ f1_forbidden_ingredients DB 조회 (유지)
  ├─ 공공데이터 API 병행 확인 (2중 안전망)
  └─ 적중 시 → 즉시 수입불가, 파이프라인 종료

[Step B] 원재료 허용 여부 + 성분코드 + GMO
  ├─ 수입식품 원료정보 API (15111777) — 사용가능여부, 제한여부, 사용조건
  ├─ 수입식품 성분코드 API (15094202) — CPNT_CD 조회, UI 표시
  └─ 식품 원재료 정보 조회 API (15111913) — GMO 여부 → F3 전달용 플래그 생성

[HITL-1] 불확실 원재료 검토
  ├─ unidentified 원재료 목록
  └─ 담당자 액션: 허용 / 금지 직접 판정

[Step C] 기준규격 수치 비교
  └─ 식품첨가물 기준규격 현황 API (15116583)

[Step D] 법령 인용 (표시 전용)
  └─ Pinecone RAG (판정 주도 X)

[HITL-2] 최종 수입 판정 확정
  └─ 담당자 결정: 수입가능 / 수입불가 / 보류 + 사유 + 전자서명
```

## 6. 에러 처리 (오류 계층)

### 6-1. 명시적 차단 (400 Error)

| 케이스 | 감지 지점 | 에러 코드 |
|--------|-----------|-----------|
| F0 pipeline_steps 없음 | F1/F2 `/run` | `F0_NOT_COMPLETED` |
| `ingredients[]` 비어있음 | F1 `/run` | `NO_INGREDIENTS` |
| `export_country` 없음 | F3 `/run` | `NO_ORIGIN_COUNTRY` |
| `food_type_hierarchy` 없음 | F3 `/run` | `FOOD_TYPE_MISSING` |

### 6-2. 조용한 폴백 (Silent Fallback)

| 필드 | 누락 시 기본값 | 하위 영향 |
|------|---------------|-----------|
| `is_oem`, `is_first_import`, `is_organic` | `False` | F3 서류 매칭 편향 |
| `alcohol_percentage` | `None` | F2 `is_alcohol` 판정 부정확 |
| `part`, `sub_ingredients` | `None` / `[]` | Step B 매칭 정확도 저하 |
| `ratio` 숫자 변환 실패 | `percentage=None` | 집계 함량 계산 누락 |

### 6-3. 의미적 오류 (구조적 감지 불가) 🚨

→ §7 리스크 섹션에서 별도 처리

## 7. 구조적 리스크 및 완화 방안

### 7-1. 리스크 목록

| ID | 리스크 | 감지 가능성 | 영향 |
|----|--------|-----------|------|
| R1 | 원재료배합비율표 슬롯에 제조공정도 업로드 (doc_type 오매칭) | **낮음** | ingredients 엉터리 or 공백 |
| R2 | 제조공정도=과자, 원재료배합비율표=햄 (제품 불일치) | **매우 낮음** | 전체 판정 왜곡 |
| R3 | `export_country="미합중국"` 오타 | **낮음** (국가 그룹 매칭 실패만 보임) | 서류 누락 |
| R4 | 원재료명 OCR 오인식 (`"대두"` → `"대수"`) | **낮음** (매칭 실패만 보임) | unidentified 증가 |
| R5 | `food_type` LLM 오분류 (`"액상차"` → `"침출차"`) | **낮음** | 기준규격 잘못 적용 |
| R6 | `ratio` 숫자 오류 (5% → 50%) | **불가** | 기준규격 비교 왜곡 |

### 7-2. 왜 자동 해결이 어려운가

| 접근 | 한계 |
|------|------|
| doc_type 키워드 검증 | 제조공정도도 "원재료" 단어 포함 → false positive/negative 흔함 |
| 제품명 교차검증 | OCR 오인식 + 문서마다 제품명 표기 다름(품목명/브랜드명/제품명) |
| LLM 자체 감지 | 확신 못 하고 hallucinate 위험 |
| 규칙 기반 | 유사 제품군 혼동(예: 햄 vs 소시지)은 규칙으로 못 잡음 |

**근본 원인:** 담당자가 파일을 잘못 올린 건지 제품이 정말 그런 건지 시스템은 알 방법이 없음. Ground truth가 존재하지 않음.

### 7-3. 현실적 완화 전략

**① 얕은 휴리스틱 경고 (차단 아님)**
- doc_type별 최소 키워드 부재 감지 (예: 원재료배합비율표 → "%", "배합", "원재료" 중 하나 이상 필수)
- 제품명 문자열 거리 측정 (Levenshtein) → 임계치 초과 시 경고
- 경고는 표시만, 차단하지 않음 (담당자 판단 위임)

**② HITL-0 단계 명시화 (핵심 방어선)**
- 현재: F0 파싱 결과 조회/수정 UI는 있으나 **검토가 선택적**
- 제안: F1 실행 전 **담당자의 F0 결과 승인**을 필수 전제조건으로 승격
- 승인 액션은 `pipeline_steps('0').status` 를 `completed` → `approved` 로 전이시키는 형태로 구현
- 검토하지 않으면 F1 `/run`이 `F0_NOT_APPROVED` 에러로 차단

**③ 결정 로그 (감사 추적)**
- 담당자가 F0 파싱 결과를 수정하면 원본과 수정본을 모두 보관
- HITL-2 PDF 보고서에 F0 수정 이력 포함 → 사후 검증 가능

### 7-4. 채택 결정

**①, ②는 재설계 범위에 포함, ③은 차후 감사 요구사항 발생 시 추가.**
