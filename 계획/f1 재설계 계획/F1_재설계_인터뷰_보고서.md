# F1 기능 재설계 — 인터뷰 보고서

> 작성일: 2026-04-19  
> 방법: Socratic Interview (ouroboros:interview Path B)  
> 대상: F1 수입 가능 여부 판정 기능 전면 재설계

---

## 1. 재설계 배경 및 근본 원인

| 문제 | 설명 |
|------|------|
| **로직 정확도 문제** | 원재료 매칭·기준규격 비교 결과 신뢰 불가 |
| **데이터 소스 부족** | Supabase DB 커버리지 부족 → unidentified 과다 발생 |
| **식품유형 분류 불가** | LLM 분류 결과 자체가 틀림, 신뢰 불가 |

---

## 2. 설계 철학

- **HITL 절대 준수**: AI는 정보 제공·집계만 담당. 수입가능 여부 최종 판단은 전적으로 담당자
- **데이터 신뢰성 우선**: 수작업 DB → 공공데이터 공식 API로 교체
- **F2 분리 원칙**: 식품유형 분류는 F2가 전담, F1은 F2 결과를 수신만

---

## 3. Non-Goals (재설계 범위 외)

- 합성향료 허용 여부 자동 판단 (HITL로만 처리)
- 기준규격 DB(f1_additive_limits, f1_safety_standards) 자체 유지보수
- 식품유형 LLM 자동 분류 (step0_food_type.py 폐기)
- RAG가 수입가능 여부를 직접 판정하는 기능

## 6. F0 → F1 입력 데이터

F0 파싱 단계에서 다음이 완료된 상태로 F1에 전달됨:

- 원재료 목록 (이름 한국어 정제 완료, 함량 비율, INS/CAS 번호)
- 공정 코드 (가열·증류·발효 여부)

F1이 추가로 필요로 하는 선행 조건:
- **F2 완료 결과** (식품유형 대·중·소 확정)

---

## 7. F2 연관 관계

| 항목 | 내용 |
|------|------|
| F2 역할 | 식품유형(대·중·소) 분류 전담 |
| F1 의존성 | F2 완료 전 F1 실행 **차단** (blocking) |
| 식품유형 HITL | F2 내에서 담당자가 확정 (F1은 확정된 결과만 수신) |
| F2 코드 수정 | 가급적 금지. 인터페이스(출력 포맷)만 명세 준수 |

## 8. 새 파이프라인 설계 (High-Level)

```
[전제조건 확인]
  ├─ F0 status = completed ✓
  └─ F2 status = completed ✓  ← 미완료 시 F1 실행 차단

[Step A] 금지원료 체크 (최우선)
  ├─ f1_forbidden_ingredients DB 조회
  ├─ 공공데이터 API 병행 확인 (2중 안전망)
  └─ 적중 시 → 즉시 수입불가, 파이프라인 종료

[Step B] 원재료 허용 여부 조회
  ├─ 공공데이터 API (수입식품 원료정보, 성분코드)
  ├─ per-ingredient 조회
  └─ verdict: 허용 / 금지 / 조건부 / 미확인

[HITL-1] 불확실 원재료 검토
  ├─ 미확인(unidentified) 원재료 목록 표시
  └─ 담당자 액션: 허용 / 금지 직접 판정

[Step C] 기준규격 수치 비교
  ├─ 공공데이터 API 실시간 조회 (식품유형 + 원재료 조합)
  └─ 결과: pass / fail / no_data

[Step D] 판정 근거 법령 인용
  ├─ Pinecone RAG 검색
  └─ 결과: 관련 법령 청크 목록 (표시 전용, 판정 주도 X)

[HITL-2] 최종 수입 판정 확정
  ├─ AI 제공 정보: 원재료 허용여부, 기준규격, 법령 인용, 금지원료 여부
  └─ 담당자 결정: 수입가능 / 수입불가 / 보류 + 사유 작성 + 전자서명
```

## 9. HITL 포인트 정의

| 포인트 | 트리거 조건 | 담당자 액션 |
|--------|-----------|-----------|
| **HITL-1** 불확실 원재료 | unidentified 원재료 1건 이상 | 허용 / 금지 직접 판정 |
| **HITL-2** 최종 판정 | 항상 (모든 케이스) | 수입가능 / 불가 / 보류 + 사유 |

> 합성향료는 HITL-1에서 처리 (자동 판단 금지)
