## 2. Pydantic 모델 변경

### 2-1. `Ingredient` (models/judgment.py)

기존 필드 유지 + **신규 추가:**

| 필드 | 타입 | 설명 |
|------|------|------|
| `component_code` | `Optional[str]` | 15094202 성분코드 `CPNT_CD` (UI 표시용) |
| `allow_verdict` | `Literal["allowed","restricted","prohibited","unidentified"]` | Step B 결과 |
| `restriction_condition` | `Optional[str]` | `CHRTR_INFO_CONT` (HITL-1 표시) |
| `edible_parts` | `Optional[str]` | `EDIBLE_USE_CONT` (사용 부위) |
| `is_gmo` | `Optional[bool]` | 15111913 `GMO_YN` 조회 결과 |
| `source_api` | `Optional[str]` | 매칭된 API id (감사 추적) |

> F0 → F1 변환 필드(`part`, `sub_ingredients`)는 이미 추가 완료됨.

### 2-2. `ProcessConditions`

기존 유지. `alcohol_percentage` 이미 추가 완료.

### 2-3. `Feature1Output` — 신규 필드

| 필드 | 타입 | 설명 |
|------|------|------|
| `gmo_ingredients` | `list[str]` | GMO=Y인 원재료명 리스트 (F3 전달용) |
| `api_call_stats` | `dict[str, int]` | endpoint_id별 호출 건수 (감사) |
| `data_source_versions` | `dict[str, str]` | 각 API의 `LAST_UPDT_DTM` 등 최신 스냅샷 (향후 감사 대비) |

### 2-4. `StandardCheck` — 필드 정비

| 필드 | 변경 |
|------|------|
| `test_category` | 신규 — `T_KOR_NM` 값 ("함량", "성상" 등) |
| `spec_raw` | 신규 — `SPEC_VAL` 원본 |
| `spec_summary` | 신규 — `SPEC_VAL_SUMUP` |
| `is_dangerous` | 신규 — `INJRY_YN=Y` |
| `unit_original` / `unit_normalized` | 분리 — 원본 단위 및 정규화 단위 |

## 3. Supabase 스키마 변경

### 3-1. 폐기 대상 테이블

| 테이블 | 폐기 방식 |
|--------|----------|
| `f1_allowed_ingredients` | 읽기 코드 제거 후 DROP (운영 관찰 2주 후) |
| `f1_additive_limits` | 동일 |
| `f1_safety_standards` | 동일 |
| `f1_ingredient_synonyms` | 동일 |

**유지:**
- `f1_forbidden_ingredients` — 2중 안전망 (API와 교차 확인)
- `pipeline_steps`, `cases` — 전체 공용

### 3-2. 신규 테이블

```sql
-- 공공데이터 API 응답 캐시
CREATE TABLE f1_data_go_kr_cache (
    cache_key       TEXT PRIMARY KEY,
    endpoint_id     TEXT NOT NULL,           -- '15111777' 등
    request_params  JSONB NOT NULL,
    response_body   JSONB NOT NULL,
    created_at      TIMESTAMPTZ DEFAULT NOW(),
    expires_at      TIMESTAMPTZ NOT NULL
);
CREATE INDEX idx_cache_expires ON f1_data_go_kr_cache (expires_at);

-- API 호출 로그 (Rate limit 추적)
CREATE TABLE f1_data_go_kr_call_log (
    id              BIGSERIAL PRIMARY KEY,
    endpoint_id     TEXT NOT NULL,
    case_id         UUID REFERENCES cases(id),
    cache_hit       BOOLEAN NOT NULL,
    status_code     INT,
    duration_ms     INT,
    called_at       TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX idx_call_log_called_at ON f1_data_go_kr_call_log (called_at);
```

### 3-3. 기존 테이블 확장

```sql
-- pipeline_steps: F0 승인 상태 추가 (HITL-0 대응)
-- status enum 에 'approved' 추가 (기존 'completed' 보다 강한 상태)
```

> 기존 `status='completed'` 값은 그대로 유지하되, HITL-0 도입 후 `status='approved'`를 F1 실행 전제로 변경. 상세는 `05_HITL_플로우_설계.md` 참조.

## 5. 마이그레이션 순서

1. **P1 시작 시:** 신규 테이블 생성 (`f1_data_go_kr_cache`, `f1_data_go_kr_call_log`)
2. **P2 시작 시:** Pydantic 모델 확장 + frontend 타입 추가
3. **P4 통합 테스트 통과 후:** 폐기 대상 테이블 READ 코드 제거
4. **P5 관찰 기간 (2주) 후:** 폐기 대상 테이블 DROP
