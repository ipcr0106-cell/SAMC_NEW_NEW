## 0. TL;DR

진단된 27개 결함의 **상·하류 의존성**을 분석하면, 사용자가 경험한 "결과가 전부 이상함" 증상은 **두 가지 진짜 원인**에서 파생된다:

```
원인 #1. 매칭 엔진 Stage 1만 작동      (매칭 층)
         └─ 원재료 식별 실패가 상시 발생
            └─ 키워드 오염 → 법령 조회 부정확
                │
                ▼
원인 #2. F1_RAG_VERDICT_DISABLED=true  (설정 층 — 결과)
         └─ "RAG를 못 믿겠다"는 판단으로 판정 주도에서 제거
            └─ 법령이 UI에 나열만 되고 판정에 영향 없음
```

**중요**: 원인 #2는 독립 원인이 아니라 원인 #1의 **결과**다. 따라서 flag를 단순히 켜는 게 아니라, 매칭을 먼저 복구한 뒤 법령 품질을 재검증하고 그 다음 flag 해제를 검토해야 한다.

## 1. 왜 27개 결함이 아니라 "2개 원인"인가

27개 결함은 **상호 독립적이지 않다**. 상류 결함이 하류 결함을 유발하거나 증폭시킨다:

```
[매칭 층 결함]                [법령 층 결함]
 ├─ #2 Stage 1만 작동          ├─ #4 필터 붕괴
 ├─ #17 Fuzzy dead             ├─ #5 기준↔법령 분리
 ├─ #19 재매칭 부재              └─ #14 RAG_VERDICT_DISABLED
 └─ #7,8,10 Step A 결함                      ▲
             │                               │
             └─ 키워드 오염 ─────────────────┘
```

### 1.1 결함 간 인과 체인

1. **매칭 실패** → 원재료 식별 키워드가 부정확
2. **부정확한 키워드** → Step D 법령 조회가 엉뚱한 법령 반환
3. **엉뚱한 법령** → "RAG 품질이 낮다"는 판단 근거
4. **낮은 품질** → `F1_RAG_VERDICT_DISABLED=true`로 판정 주도에서 제외
5. **제외된 법령** → UI에는 표시되지만 판정엔 기여 안 함 → 실무자 혼란

즉 **원인 #1을 고치지 않으면 원인 #2의 flag를 풀어도 여전히 결과가 이상**하다.

### 1.2 나머지 24개 결함의 성격

- **증폭 효과** (API Silent masking #1, gather 타임아웃 #6): 원인 #1·#2의 증상을 키움
- **2차 파생** (중복 제거 없음, top_k 이중제한, MIN_SCORE 약함): 법령 노이즈 악화
- **UX 증상** (기본 펼침, 근거 보기 부재, 접근성): 최종 인지 부하
- **인프라 채권** (CI 없음, conftest 없음, 감사 로그 INSERT 없음): 복구 방해

이들은 **두 원인의 결과 또는 증폭기**로 해석할 수 있다.

## 2. 진짜 원인 #1 — 매칭 Stage 1만 작동

### 2.1 증상

- 사용자 보고: **"밀가루 같은 흔한 원재료도 매칭 실패가 남용될 정도로 흔함"**
- 스크린샷 증상: 원재료 "밀가루"가 미확인 상태로 표시 (S6)

### 2.2 코드 근거

이상적 매칭은 6단계 계단이어야 한다:

```
Stage 1: 정확 매칭           ← 현재 유일하게 작동
Stage 2: 정규화 매칭         ← 부분 작동 (normalize_name)
Stage 3: Fuzzy 매칭          ← dead code
Stage 4: 3-key 교차          ← 미구현
Stage 5: LLM 정규화 제안     ← 미구현
Stage 6: 실무자 개입 (HITL)  ← 존재 (단, 재매칭 없음)
```

**Dead code 목록**:
- `_levenshtein()` (f1_step_b.py:141~169): 함수 정의만, 호출 없음
- `_match_ingredient_hits()` (f1_step_b.py:347~355): 존재하나 `run_step_b()`에서 호출 안 됨
- `_lookup_synonym()` (f1_step_b.py:52~96): 정의만 있고 호출 경로 완전 부재

### 2.3 언제·왜 폐기됐는가

**P6-b 재설계에서 data.go.kr 15111777 API를 제거**할 때, 해당 API에 의존하던 fuzzy/synonym 호출 경로가 함께 폐기되었다. 코드는 남아있지만 호출 진입점이 사라졌다. 테스트 파일 `test_f1_step_b.py`에서 8개 케이스가 `_LEGACY_15111777` 마크로 skip 상태다.

### 2.4 Step A의 2차 매칭 결함

Step A(금지 원재료 판정)도 같은 문제를 겪는다:
- `f1_step_a.py:75~78`: `.select("name_ko, reason, law_source")` — `aliases` 컬럼을 SELECT조차 안 함
- `f1_step_a.py:76`: `name_en` 미조회 → "Cannabis", "Opium poppy" 영문 입력 회피

**구체적 false negative 시나리오**:

| 입력 | 기대 | 실제 | 원인 |
|---|---|---|---|
| "마리화나" | 금지 hit ("대마초" aliases에 존재) | 통과 | aliases 미조회 |
| "Cannabis" | 금지 hit | 통과 | name_en 미조회 |
| "센나" | 주의 (restricted) | 주의 | 정상 |
| "센나잎" | 금지 hit | 금지 hit | 정상 (정확 매칭 작동) |

### 2.5 파급 효과

원재료 식별 실패가 광범위하게 발생하면:
1. Step D 법령 조회 키워드가 부정확해진다 (#2 → #4 연쇄)
2. 판정 근거가 부실해진다 (#2 → #5)
3. unidentified 폭증 → 실무자가 수동으로 대체원재료명을 쳐야 함 (HITL 부담 폭증)
4. 재매칭 기능도 없어(#19) 실무자가 수동으로 F1 재호출해야 함

## 3. 진짜 원인 #2 — F1_RAG_VERDICT_DISABLED=true

### 3.1 증상

- 사용자 보고: **"법령 인용은 정확하나 중요도가 낮은 정보를 너무 많이 가져오는 경우가 다수"**
- 스크린샷 증상: 법령 5건이 UI에 나열되지만 기준규격 5건과 1:1 연결되지 않음 (S5)

### 3.2 flag의 의미

`backend/config/feature_flags.py:53~65` 참조:

| Flag | 현재값 | 의미 |
|---|---|---|
| `F1_RAG_VERDICT_DISABLED` | `true` | Step D RAG가 "표시 전용" 모드. 법령 인용이 판정 결정에 기여하지 않고, 단순 근거 표시용으로만 사용됨 |

### 3.3 flag가 켜진 이유 (추정)

프로젝트 메모리에 다음 기록이 있다:

> F1 DB 신뢰 불가 — f1_* 테이블 판정 근거 사용 금지. 외부 API 기반 판정으로 전환 필수.

이는 RAG 품질 부족으로 인해 **"일단 판정 주도에서 제외하자"**는 과도기적 결정을 의미한다.

그러나 **RAG 품질이 부족한 근본 이유는 원인 #1 (매칭 실패)에서 온다**. 매칭이 부정확하면 RAG가 받는 키워드가 오염되고, 오염된 키워드로는 좋은 법령을 찾아낼 수 없다.

### 3.4 파급 효과

- 법령이 판정 근거로 쓰이지 않고 UI에 나열만 됨
- 실무자 입장에서는 "정확해 보이는 법령이 많은데 판정 결과에 안 반영된 것처럼 보임" → 혼란
- HITL 철학상 "근거를 보고 판단"해야 하는데, **근거와 판정이 분리됨**

## 4. 두 원인의 의존성

### 4.1 의존 방향

```
매칭 복구 (원인 #1)  →  RAG 품질 회복  →  flag 해제 검토 (원인 #2)
    ↑ 상류                                     ↓ 하류
```

### 4.2 잘못된 순서 (flag 먼저 해제)

```
flag만 해제       →  오염된 키워드로 법령 조회  →  엉뚱한 법령이 판정 주도
(매칭은 그대로)                                 → 증상 악화
```

### 4.3 올바른 순서

```
Step 1. 매칭 Stage 2~5 복구          → 키워드 품질 상승
Step 2. Silent masking 제거           → 실패가 UI에 노출됨 → 디버그 가능
Step 3. 법령 필터 강화 + dedup        → S/N 개선
Step 4. RAG 품질 재측정 (골든셋)      → 합격 시 flag 해제 검토
```

### 4.4 실행 계획과의 연결

- Step 1 → Wave A-1, A-3
- Step 2 → Wave A-2
- Step 3 → Wave A-4
- Step 4 → Wave A-5

상세는 [f1-redesign-plan-2026-04-20.md](./f1-redesign-plan-2026-04-20.md) 참조.

## 5. "결과가 전부 이상" 증상의 5층 누적 메커니즘

```
[L1 API 층]
  Silent masking (결함 #1) + gather 무제한 (결함 #6)
  → "성공이지만 빈 응답" 상시 발생
  → 다음 층에 빈 데이터를 넘김
        ↓
[L2 매칭 층]
  Stage 1만 작동 (결함 #2) + aliases·영문명 미조회 (결함 #7, #8)
  → 흔한 원재료도 식별 실패
  → 다음 층에 부정확한 원재료 식별자를 넘김
        ↓
[L3 기준규격 층]
  키워드 조인 (FK 없음) + 단위 문자열 통째 저장
  → 엉뚱한 기준이 붙거나 환산이 안 됨
  → 다음 층에 오염된 기준치를 넘김
        ↓
[L4 법령 인용 층]
  약한 필터 (결함 #4) + 중복 제거 없음 + RAG_VERDICT_DISABLED (결함 #14)
  → 관련성 낮은 인용이 UI에 대량 노출
  → 다음 층에 노이즈를 넘김
        ↓
[L5 UI 층]
  기본 펼침 + 계층 없음 (결함 #22) + 접근성 없음 (결함 #23)
  → 실무자 인지부하 폭증
  → HITL 개입 불가

실무자 체감: "결과가 전부 이상해서 개입할 수 없다"
```

각 층의 실패가 **다음 층에 누적**되므로 단일 층만 고쳐서는 증상이 사라지지 않는다. 반대로 상류부터 순차 복구하면 각 층에서 누적 효과로 품질이 배가된다.

## 6. HITL 철학과의 충돌 지점

### 6.1 설계 철학 재확인

> 현단계의 부족한 AI 판단을 실무자가 최종적으로 결정하는 것이 핵심이다.

### 6.2 HITL이 작동하는 3가지 전제

```
정상 HITL:
  AI 80% 정확 → 실무자가 20% 보정 → 빠른 최종 판정

  필수 조건:
  ① AI 결과의 기본 신뢰도가 높다 (시작점 확보)
  ② 각 단계에서 실무자가 채택·수정·기각 가능 (개입 접점)
  ③ 근거가 투명하게 표시된다 (판단 가능)
```

### 6.3 현재 상태의 3가지 충돌

```
현재 상태:
  AI 결과 신뢰도 부족 → 실무자가 시작점 못 잡음 → HITL 붕괴

  각 전제의 붕괴:
  ① 매칭 실패·법령 오염으로 AI 결과가 "이상함" (원인 #1)
  ② 근거 보기 UI 부재로 "왜 이 판정?"을 확인 불가 (결함 #22)
  ③ 법령이 판정 주도에서 빠져 근거·판정이 분리됨 (원인 #2)
```

### 6.4 HITL 복원의 3단계

| 단계 | 목표 | 대응 Wave |
|---|---|---|
| 1단계 | AI 기본 신뢰도 회복 | Wave A (매칭·필터 복구) |
| 2단계 | 개입 접점 추가 | Wave B (기준↔법령 연결, 근거 보기 모달) |
| 3단계 | 근거-판정 일관성 | Wave A-5 (RAG를 판정 주도로 재편입) |

각 단계는 HITL의 세 전제를 되살리는 작업에 1:1 대응한다.

## 7. 원인 분석의 신뢰도

본 원인 분석은 **27개 결함 각각의 파일:라인 근거**와 **결함 간 상·하류 의존성 논증**을 기반으로 한다. 다만 다음 전제가 유지될 때만 유효하다:

- 사용자가 보고한 증상 (S1~S7, "결과가 전부 이상")이 실제 실무 상황의 대표적 케이스
- F2 자동분류 정확도 80%+ 주장이 유효 (F2는 원인 후보에서 제외됨)
- 3차 에이전트 탐색 당시 코드 상태가 변경되지 않음 (BC 브랜치 기준)

전제 중 하나라도 흔들리면 원인 재분석이 필요하다.
